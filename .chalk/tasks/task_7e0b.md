Follow-up from task_d8d6 / PR #91 (Pi 1.3 -> 1.4.0).

## Findings (tech lead, 2026-10-28)
- **The exit-1-on-length premise does NOT apply to us.** In Pi 1.4 `dist/modes/print-mode.js`, the "Response was truncated" + `exitCode = 1` path is inside `if (mode === "text")`. We run `pi -p --mode json` (docker/reviewer/entrypoint.sh), and Pi's docs/cli-integration.md says JSON mode does not exit nonzero for a failed/aborted/truncated response by itself. So a length-truncated run still exits 0 and reaches the #89 `describeMissingReport` path. No behaviour change needed, but it's fragile: if any future non-zero exit happens after turns streamed, the non-zero branch throws all diagnostics away and reports only the stderr tail.
- **willRetry is a real undercount.** Pi docs/json.md: `agent_end.messages` = "messages generated by the run" (that one low-level run only), and `agent_end` can be followed by auto-retry/overflow recovery (`willRetry: true`). `reviewer.ts` overwrites `agentEndMessages` on each `agent_end` and then summarises usage from the LAST one's assistant messages, so with a retry the failed attempt's tokens/turns are dropped from telemetry. `streamedMessages`/`assistantMessages` (every `message_end`) already span all runs.

## Plan
- [ ] `reviewer.ts` close handler: derive `messages` (usage, last-turn error check, summary fallback) from the streamed `assistantMessages`, falling back to the last `agent_end` assistant messages only when nothing streamed. Update the NDJSON-parsing comment block (agent_end is per-run, not authoritative-for-whole-run) and the `agentEndMessages` comment.
- [ ] Non-zero exit branch: when assistant turns streamed, include the `describeMissingReport` diagnostic (bounded, redacted) ahead of the stderr tail in the reason, so a future exit-1-on-length (or a crash after turns) keeps the cause. Keep the existing `review container exited with code N` prefix (tests/telemetry may match it).
