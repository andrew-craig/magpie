## Background

Filed out of M8-E7's review (`task_80a4`, closed 2026-07-31). M8-E4
(`task_4c37`, PATH) and M8-E7 (`task_80a4`, `MAGPIE_FINDINGS_PATH`) were the
same defect discovered twice, one live micro-VM run at a time.

## Problem

The crun floor runs the reviewer **image**, so the OCI image config applies:
`ENV`, `WORKDIR`, and the base image's implicit `PATH` are all delivered by the
runtime. The micro-VM tier runs an **exported bare rootfs** — libkrun has no
image config to read, so none of that surface arrives unless something
re-declares it. Each missing piece fails late, inside the guest, and is only
diagnosable from guest stderr (which itself only exists because of M8-E6).

Known instances, both already fixed: `PATH` (M8-E4) and `MAGPIE_FINDINGS_PATH`
(M8-E7), each re-exported in `docker/reviewer/entrypoint.sh` under the
`MAGPIE_IS_MICROVM` guard. `WORKDIR /work` is *not* an instance — `reviewer.ts`
passes `--workdir /work` explicitly and `reviewer-microvm-argv.test.ts` pins it.

The point of this task is not to find a third live bug — as of the M8-E7 build
the surface is believed complete — it is that nothing **stops** a fourth from
being introduced. Add an `ENV` to the Dockerfile today and the micro-VM tier
loses it silently, with no test failing.

## Proposed work

- [x] Enumerate the full image-config surface the crun tier gets and the
      micro-VM tier does not: every `ENV` in `docker/reviewer/Dockerfile`
      (currently just `MAGPIE_FINDINGS_PATH`), the base image's implicit `PATH`,
      `WORKDIR`, `USER`/uid, and `ENTRYPOINT`/`CMD` argv. Record which mechanism
      delivers each one to the micro-VM guest today (entrypoint re-export,
      launcher flag, or nothing).
- [x] Add a **drift test** that fails when the two diverge: parse the
      Dockerfile's `ENV` lines and assert each is either re-declared in
      `entrypoint.sh`'s `MAGPIE_IS_MICROVM` block or injected by `reviewer.ts`.
      This generalises `entrypoint-tier-memory.test.sh`'s existing one-variable
      pin (which asserts the `MAGPIE_FINDINGS_PATH` literal matches the
      Dockerfile) into a check that cannot be outgrown by a new `ENV`.
- [x] Document the contract in the Dockerfile next to the `ENV` block: "anything
      added here must also be re-declared for the micro-VM tier — see
      entrypoint.sh."
- [x] No behaviour change expected. If the audit does turn up a live gap, fix it
      under this task and re-validate on the Pi host; otherwise the deliverable
      is the guard plus the audit record.

### What was built

- `packages/orchestrator/src/docker-image-config-drift.ts` — pure, documented
  parsing/checking functions: `parseDockerfileEnvVars` (extracts `ENV
  NAME=value` lines), `extractMicrovmGuardedBlocks`/`isReexportedForMicrovm`
  (finds `export NAME=...` inside entrypoint.sh's `MAGPIE_IS_MICROVM`-guarded
  blocks, correctly excluding an `else` branch and handling nested `if/fi`),
  `isInjectedByReviewerTs` (finds `env`/`envFromHost` entries at
  reviewer.ts's `buildMicrovmLaunchArgs` call site), and
  `findUncoveredMicrovmEnvVars` (the actual guard: Dockerfile ENV names
  covered by neither mechanism). Each function's doc comment is explicit
  about which real-world Dockerfile/bash/TS forms it does and does not
  understand — this is a targeted regression guard, not a general parser.
- `packages/orchestrator/src/reviewer-microvm-env-parity.test.ts` — a real
  **vitest** test (not just a shell script) that:
  - runs the guard against the REAL on-disk `Dockerfile`/`entrypoint.sh`/
    `reviewer.ts` and asserts `findUncoveredMicrovmEnvVars(...) === []`;
  - unit-tests each parsing/checking function against small fixtures
    (including a false-positive check: the docker-client's own `const env:
    NodeJS.ProcessEnv = {...}` and the `env`/`envFromHost` TYPE-annotation
    positions in reviewer.ts must NOT be mistaken for the micro-VM
    call-site's `env`/`envFromHost` object/array literals);
  - **proves the guard actually trips**: a fixture Dockerfile with an extra,
    genuinely-uncovered `ENV MAGPIE_NEW_THING=...` is asserted to produce
    `["MAGPIE_NEW_THING"]`, then shown to go silent once covered via either
    mechanism (entrypoint.sh re-export OR reviewer.ts injection).
  - This lives under `packages/orchestrator/src/`, alongside
    `reviewer-crun-floor-argv.test.ts`/`reviewer-microvm-argv.test.ts`, so
    `npm test` (vitest across workspaces) picks it up automatically — this
    is the file that makes the guard an actual CI merge gate, per the task's
    critical design steer.
- **`.github/workflows/ci.yml`**: added `docker/reviewer/**` to both the
  `push` and `pull_request` `paths:` filters. Caught during verification:
  without this, a PR touching ONLY `docker/reviewer/Dockerfile` (e.g. adding
  a new `ENV` with no accompanying `packages/` change) would never trigger
  `ci.yml` at all — the new test would exist but never actually run on the
  PR that needs it, silently defeating the guard. This was a real,
  previously-unnoticed gap in the existing CI wiring (not unique to this
  task — `reviewer-crun-floor-argv.test.ts`'s golden had the same latent
  exposure for any Dockerfile-only drift), fixed as part of making this
  guard meaningful.
- `docker/reviewer/Dockerfile`: added a "CONTRACT (M8-E8, task_0208)" comment
  directly above `ENV MAGPIE_FINDINGS_PATH=...` documenting that anything
  added to this `ENV` block must also be covered for the micro-VM tier (via
  `entrypoint.sh` or `reviewer.ts`), naming the new test that now enforces
  it, and cross-referencing the two prior live defects (M8-E4, M8-E7) this
  guard exists to prevent a third occurrence of.
- Left unchanged: `docker/reviewer/entrypoint-tier-memory.test.sh` (still
  passes unmodified, 22/22) — its `MAGPIE_FINDINGS_PATH` value-pin is still
  useful (it also checks the exported VALUE matches, which the new coverage
  check does not) and was not folded into the vitest test per the task's own
  framing ("you may ALSO extend it... but the vitest test is the deliverable
  that matters").
