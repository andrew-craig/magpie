## Background

Found during a full reinstall + live validation of `main` on the Pi host
(2026-07-30, see memory `magpie-m8-reinstall-validation`). This is blocker
#2 of 3 for the micro-VM tier — reached only after building a current image
(task_1709).

## Problem

`docker/reviewer/entrypoint.sh`'s memory-ceiling assertion (added for
bug_df2d) reads `/sys/fs/cgroup/memory.max` and aborts if it's
absent/unreadable — correct for the crun tier (podman `--memory`, cgroup v2
enforced) but **structurally inapplicable** to the micro-VM tier: RAM there
is enforced by libkrun's `--ram-mib` at the VMM level, so the guest never has
a `/sys/fs/cgroup/memory.max` to read at all — it's not a misconfiguration,
it's a different (equally valid) enforcement mechanism.

The check runs *before* the entrypoint's own `MAGPIE_IS_MICROVM` detection
(`/dev/vsock` probe), so it can't distinguish "cgroup missing because this is
a micro-VM guest with VMM-enforced RAM" from "cgroup missing because the
crun-tier host misconfigured cgroups" (the real bug_df2d scenario it exists
to catch).

Current workaround (used during validation): set
`[container] require_memory_limit = false` globally. This works, but it's a
blunt instrument — it also disables the crun-tier's real protection if an
operator forgets to flip it back (I hit this directly: after testing the
micro-VM tier I had to remember to restore
`require_memory_limit = true` before leaving the crun floor as the resting
state). `require_memory_limit` is tier-global; it should be tier-aware.

## Fix

Reorder the entrypoint so the `/dev/vsock` (`MAGPIE_IS_MICROVM`) probe runs
**before** the memory-ceiling check, then branch:
- crun tier: today's behavior unchanged (cgroup `memory.max` check, gated by
  `MAGPIE_REQUIRE_MEMORY_LIMIT`).
- micro-VM tier: verify RAM is *actually* VMM-enforced by some equivalent
  positive check (e.g. assert `ram_mib` was passed and is finite, or that no
  guest-visible cgroup override exists) rather than skipping verification
  entirely — the goal is "prove SOME ceiling is enforced," not "give up
  checking because cgroups don't apply here."
- Consider whether `require_memory_limit` should become tier-scoped in
  config (e.g. implicitly true-but-differently-verified for microvm) so a
  single flag can't accidentally disable crun's real protection while
  working around a micro-VM non-issue.

## Acceptance

- Micro-VM tier boots without needing `require_memory_limit = false`.
- crun tier's existing enforcement/tests (bug_df2d's regression coverage)
  unaffected.
- A micro-VM-tier live review gets past this check without an operator
  having to weaken the crun tier's real protection to do it.

**Memory-check tolerance chosen:** 5% above the configured `ram_mib`
(`ram_mib * 1024 * 105 / 100` KiB). Guest `MemTotal` is always somewhat
*less* than the configured ram-mib (kernel/firmware-reserved regions), never
more — the failure mode being defended against is `MemTotal` far exceeding
`ram_mib` (meaning the VMM ceiling silently didn't apply). 5% is generous
headroom for rounding/reporting slop while still catching a materially
unenforced ceiling (e.g. the guest actually seeing host RAM).

**Verified statically:** `bash -n` + `shellcheck` clean; full orchestrator
vitest suite green (409 passed/4 skipped, including

### Setup used (and why)

Both sides of the boundary had to come from the branch, because the fix spans
them:
- `docker/reviewer/entrypoint.sh` ships INSIDE the guest rootfs → built the
  reviewer image locally from the branch with rootless podman as the `magpie`
  user, then `podman export`ed it to
  `/var/lib/magpie/reviewer-rootfs-e2e3` and pointed `[microvm] rootfs_path`
  at it. (One local-only Dockerfile edit was needed to build at all:
  `FROM rust:` / `FROM node:` had to be qualified to
  `docker.io/library/…` because this host's `registries.conf` defines no
  unqualified-search registries. That edit was made in a throwaway
  `git archive` export under `/tmp`, NOT in the repo.)
- `MAGPIE_MICROVM_RAM_MIB` injection is ORCHESTRATOR-side → the live
  `/opt/magpie` is a packed release built from `main` and does **not** inject
  it. Ran `npm run build` on the branch and rsynced `dist/` into
  `/opt/magpie/packages/orchestrator/dist` (after backing the original up),
  then reverted. Verified the env var genuinely reached the guest: the check
  reported `MAGPIE_MICROVM_RAM_MIB=1024` rather than fail-closing with "is
  unset or non-numeric".

`container.tier` was left at `"crun"`; adding `rootfs_path` was enough for the
ladder to auto-resolve `microvm` (tier is a FLOOR, not a ceiling) — confirmed
on `GET /healthz` (`resolvedTier: "microvm"`, `requestedTier: "crun"`,
`degraded: false`) before the review was triggered. `require_memory_limit`
stayed `true` throughout.
